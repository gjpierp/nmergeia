## 📉 スライド 2: データベースにおけるパフォーマンス低下の代償
* **キーポイント:**
  * **非効率的なリソース使用:** 遅いクエリはCPUを飽和させ、`shared_buffers`を消費します。
  * **ユーザーエクスペリエンス (UX):** アプリケーションの重要なエンドポイントに蓄積されたレイテンシ。
  * **クラウドコスト (FinOps):** 垂直スケーリングによってコストを削減しようとするのは、コードのチューニングに比べて悪い解決策です。
* **視覚要素:** レイテンシとCPU使用率の指数関数的な増加を示す簡略化された比較グラフ。
* **スピーカーノート:** クエリを最適化することで、データベースインスタンスの垂直スケーリングを延期でき、月々のFinOps予算に直接的な影響を与えます。

## 🔍 スライド 3: 遅いクエリの解剖学 (`EXPLAIN ANALYZE`)
* **コアコンセプト:**
  * `EXPLAIN (ANALYZE, BUFFERS)`を使用すると、実際の実行時間とディスクへの影響を測定できます。
  * **Seq Scan (シーケンシャルスキャン):** PostgreSQLはディスク全体を読み取ります。危険！
  * **Shared Read / Hit:** データベースキャッシュのミスを特定します。
* **サンプルスニペット:**
  ```sql
  EXPLAIN (ANALYZE, BUFFERS) 
  SELECT * FROM transactions WHERE user_id = 45892;
  ```
* **スピーカーノート:** 単に`EXPLAIN`を使用するだけでは不十分です。メモリと物理ディスクから読み取られたページを定量化するために、常に`ANALYZE`と`BUFFERS`を追加する必要があります。

## ⚡ スライド 4: スマートなインデックス作成 (B-Tree vs BRIN vs GIN)
* **比較表:**
  * **B-Tree:** デフォルトのインデックス。等価検索、ソート、およびカーディナリティの高い列の範囲検索に最適です。
  * **BRIN (Block Range Index):** 時系列でソートされた巨大なテーブルに最適。B-Treeよりも最大99%少ないスペースを占有します。
  * **GIN (Generalized Inverted Index):** JSONBフィールドおよびフルテキスト検索 (`tsvector`) に最適な味方。
* **スピーカーノート:** すべてにB-Treeインデックスを作成すると、ストレージが肥大化する可能性があります (index bloat)。BRINとGINは、選択的に使用する方法を知っておくべきツールです。

## 🧠 スライド 5: 本番環境でのメモリ調整
* **不変パラメータ:**
  * `shared_buffers` = 利用可能な合計RAMの25%。
  * `work_mem` = `ORDER BY`や結合`JOIN`などの操作がディスク上の一時ファイルを使用するのを防ぎます。
  * `random_page_cost` = SSD/NVMeディスクを使用するアーキテクチャでは、`4.0`から`1.1`に調整します。
* **スピーカーノート:** `random_page_cost`の値が高すぎると、プランナーはSSD上のインデックスを使用する前にSeq Scanを行うことを好むようになります。

---

## 🛠️ スライド 6: ダウンタイムなしのメンテナンス
* **ゼロダウンタイム戦略:**
  * `CREATE INDEX CONCURRENTLY`は、インデックス作成中にテーブルへの書き込み（`INSERT` / `UPDATE`）がブロックされるのを防ぎます。
  * `REINDEX TABLE CONCURRENTLY`は、オンラインで*Index Bloat*を排除することで、肥大化したインデックスを再構築します。
* **本番スクリプト:**
  ```sql
  REINDEX INDEX CONCURRENTLY idx_users_status_created;
  ```
* **スピーカーノート:** ピーク時において本番環境で単純な`CREATE INDEX`を絶対に実行しないでください。テーブル全体がロックされ、アプリがタイムアウトします。

## 📋 スライド 7: 本番リリース前のチェックリスト
* **実行する手順:**
  1. 候補のクエリに対して`EXPLAIN (ANALYZE, BUFFERS)`を実行する。
  2. インデックスなしで非効率的なネステッドループ（`Nested Loop`）が実行されていないことを確認する。
  3. 常に`CONCURRENTLY`ディレクティブを使用してインデックスを作成する。
  4. デプロイ後、`pg_stat_statements`を通じて動作を監視する。
* **スピーカーノート:** このチェックリストは、`main`ブランチへのマージを承認する前のデータベースのコードレビューの標準フローの一部である必要があります。
